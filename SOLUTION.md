# Решение

## 1. Скидки в статистике

`GET /customers/:id/daily-totals` теперь отдаёт по каждому дню
`{ date, total, gross, discount, net }`:

- `gross` — сумма `amount` оплаченных заказов (до скидки);
- `net` — сумма `amountPaid` (фактически оплачено);
- `discount = gross − net`;
- `total = gross` — оставлен для обратной совместимости.

Принятые решения:

- **`amountPaid` — источник истины для `net`.** `discountPercent` не используется
  для расчёта: процент описательный, фактическая оплата может не сойтись с ним
  на копейку из-за округления на стороне платёжной системы.
- **Нет `amountPaid` → `net = gross`**, скидки нет. Это касается старых данных и
  вебхуков без нового поля.
- **`amountPaid > amount`** спец-обработки нет: по контракту (`amountPaid` = `amount`
  со скидкой 0–100 %) это невозможно. Если upstream пришлёт аномалию, в ответе
  получится отрицательный `discount` — видимый сигнал, а не тихая подмена данных.
- Миграция `migrations/002_order_discounts.sql` добавляет `amount_paid_kop BIGINT
  NOT NULL`; существующие строки backfill'ятся как `= amount_kop` (скидки сервис
  раньше не читал).
- Все суммы и разности считаются в integer-копейках; в рубли переводятся только
  в ответе. Заодно исправлен `toKop`: `Math.floor((rub * 100).toFixed(6))` вместо
  `Math.floor(rub * 100)`, иначе `0.29 → 28`, `1.15 → 114` из-за float.

## 2. Причина расхождения у `c_7` и исправление

**Причина:** `TotalsService.daily` вычисляла **одно** смещение
`tzOffsetMinutes(timezone, new Date())` и применяла его ко всем заказам периода.
`c_7` — `Europe/Berlin`. На момент запроса (ноябрь) смещение +60 минут,
а 29.03.2026 ЕС перешёл на летнее время (+120). Поэтому заказы, созданные
в 22:00–23:00Z 29–30.03, попадали на предыдущий локальный день.

**Как нашли:**

1. Прочитали `TotalsService.daily` — единственное место, где смещение берётся
   из `new Date()`.
2. Численно проверили Europe/Berlin: `2026-03-29T22:30Z` — это `30.03 00:30`
   при смещении +2, но `29.03 23:30` при +1.
3. После прогона на реальных данных сверили эндпоинт с SQL
   `(created_at AT TIME ZONE 'Europe/Berlin')::date` — совпадение до копейки.
   Эмуляция старого алгоритма (`created_at + interval '60 minutes'`) дала
   расхождение только за 29–31.03:

| день | правильно, gross ₽ | старый код, gross ₽ |
|---|---:|---:|
| 27.03 | 24 736 | 24 736 |
| 28.03 | 58 233 | 58 233 |
| 29.03 | 34 658 | 43 964 |
| 30.03 | 59 684 | 52 201 |
| 31.03 | 35 401 | 44 064 |

Это ровно «по части дней не сходится».

**Исправление:** в `src/utils/time.ts` добавлен `localDate(at, timeZone)` —
календарная дата момента в IANA-зоне через `Intl.DateTimeFormat("en-CA", ...)`
с кэшем форматтеров. `TotalsService` теперь вызывает его для каждого заказа.
`Intl` сам выбирает смещение, действующее **на момент заказа**, поэтому:

- прямой переход (март) и обратный (октябрь) обрабатываются одинаково корректно;
- в осенней складке оба инстанта (`00:30Z` и `01:30Z` 25.10) дают одну дату —
  для суточной статистики это верно: неоднозначно только локальное время, не дата;
- результат не зависит от текущей даты запуска.

## 3. Как проверял

- `npm run typecheck` — чисто.
- `npm test` — **39 тестов в 5 файлах, все проходят**. Добавлены:
  - unit-тесты `localDate`: переход на летнее время, обратный переход, крайние
    зоны (`Pacific/Kiritimati`, `Etc/GMT+12`);
  - интеграционный регресс для `c_7`/`Europe/Berlin` с фиксацией `Date`
    (`vi.setSystemTime` на март и на июль), чтобы тест не зависел от даты запуска.
- E2E по регламенту:
  1. чистая БД: `docker compose -p orders-aggregator rm -sf postgres && docker compose -p orders-aggregator up -d`;
  2. `npm run migrate`;
  3. `POST /sync` — `{"pages":52,"received":5030,"applied":5030,"stale":0,"invalid":0}`;
  4. вебхуки из README — `webhooks sent: 92, responses: {"200":92}`;
  5. `GET /customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31` — ответ сохранён
     в `result.json` и сверен с SQL-агрегацией по `AT TIME ZONE 'Europe/Berlin'`
     (совпадение до копейки, сумма 5 дней = сумма всех оплаченных заказов).

## 4. Что ещё заметил

- Внешний API иногда отвечает `200` с телом `{ "error": "rate_limited" }` —
  клиент это ретраит как rate limit.
- `discountPercent` и `amountPaid` приходят как числа или строки — на границе
  приводим оба варианта.
- `toKop` терял копейку на float-погрешности (исправлено в части 1).
- `pending` и `refunded` не входят в статистику — по текущему контракту.
- `paidCreatedBetween` возвращает заказы без `ORDER BY` — на суммы не влияет.
- У postgres-сервиса нет named volume: «чистая БД» = пересоздание контейнера.

## 5. Допущения

- День заказа определяется по `createdAt` — другого поля в API нет.
- Если `amountPaid` отсутствует, считаем, что скидки не было (`net = gross`).
- `amountPaid > amount` не клэмпим и не отклоняем: по контракту невозможно,
  а при аномалии отрицательный `discount` будет заметен в отчёте.
- «Чистая БД» в регламенте — пересозданный контейнер PostgreSQL.

## 6. Что бы доделал при наличии времени

- Перенести агрегацию в SQL (`created_at AT TIME ZONE $tz` + `GROUP BY`) и
  добавить индекс под отчёты — меньше данных тянется в память.
- Property-тесты таймзон: южное полушарие, нецелые смещения, исторические переходы.
- Эвикция кэша форматтеров (сейчас `Map` ограничен числом зон, практически не растёт).
- Учитывать `paidAt`, если появится в API: сейчас день считается по `createdAt`.
- Мониторинг расхождений с отчётом платёжной системы.
